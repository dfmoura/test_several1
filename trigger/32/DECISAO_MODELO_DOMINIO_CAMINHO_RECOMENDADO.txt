====================================================================================================

  VEREDITO ........ MODELO DE DOMÍNIO APROVADO COMO EXCELENTE / BASELINE FECHADA
  NOTA GLOBAL ....: 9,3 / 10  (excelente para indústria flexográfica PME / ≤10 users)

                    sobre o baseline atual, com refinamentos mínimos listados
                    na seção 5 (ownership fino) — sem redesign.

  Por que é excelente (não “bom o bastante”):
    • Linguagem ubíqua consistente (ORC → PED → OP/OS → NF ≠ TIT → COB → ENT → BX)
    • PED como agregado-raiz operacional — elimina satélites e “pedido paralelo”
    • Fronteiras explícitas (fiscal oficial / LAI / EMP-00002 / CT-e fora)
    • Invariants mensuráveis (D0.1–D0.17) + SoD + idempotência dinheiro/NF
    • Bounded contexts M01–M11 alinhados a 80 UCs rastreáveis a TXT-fonte
    • Decimal, identidade dupla (id + código), multi-empresa e adapters já decididos
    • Fluxo feliz + exceção (RMA/DEV) + compras/REM modelados — não só o happy path

  O que NÃO falta agora:
    • Outro “modelo de domínio” paralelo
    • Microsserviços por módulo
    • Contabilidade oficial / SPED / eSocial completo no ERP
    • Reabrir LAI

  O que falta agora (fora de modelagem):
    • Ratificar parâmetros numéricos (direção)
    • Homologar CFOP/de-para/export com o CONTADOR
    • Implementar monólito modular conforme seção 4

2. REVISÃO POR BOUNDED CONTEXT (M01–M11)
====================================================================================================

----------------------------------------------------------------------------------------------------
2.1. M01 — CADASTROS                                          NOTA: 9,5 | DECISÃO: MANTER
----------------------------------------------------------------------------------------------------

  Força:
    • PAR único com papéis (evita cadastro duplicado cliente×fornecedor×transporte).
    • Prospect orça; PED exige cadastro completo — regra comercial realista.
    • Soft-delete; SoD em dados bancários; unidades/fatores/NCM no SKU.

  Risco residual: nenhum de modelagem — só qualidade de dados na migração.
  Caminho: implementar como base da virada (estratégia “cadastro + estoque no dia”).

----------------------------------------------------------------------------------------------------
2.2. M02 — COMERCIAL                                          NOTA: 9,7 | DECISÃO: MANTER (ÂNCORA)
----------------------------------------------------------------------------------------------------

  Força:
    • ORC versionado + cenários + gordura/alçada + imposto ESTIMADO.
    • Aceite formal por LINK (não zap) → PED com SNAPSHOT travado.
    • Crédito (FINANCEIRO) vs operação comercial (SoD) bem separado.
    • Recorrência gera novo ciclo ORC→aceite — nunca PED sozinho.

  Risco residual: calibragem de alçadas/% gordura (parâmetro, não domínio).
  Caminho: núcleo do MVP; código/eventos conforme catálogo §11 do DOMINIO.

----------------------------------------------------------------------------------------------------
2.3. M03 — PRODUÇÃO / PCP                                     NOTA: 9,2 | DECISÃO: MANTER
----------------------------------------------------------------------------------------------------

  Força:
    • OP/OS nascem do item do PED (PRODUCAO|SERVICO) — sem produção órfã.
    • Conclusão libera PA / política de faturamento.
    • Amostra/CQ/manutenção como S (fase 2) — escopo MVP limpo.

  Risco residual: BEM aparece também em Gerencial (ver §5.2 — ownership decidido).
  Caminho: FASE 1 = OP/OS/apontamento/conclusão; preventivo e amostra depois.

----------------------------------------------------------------------------------------------------
2.4. M04 — ESTOQUE                                            NOTA: 9,4 | DECISÃO: MANTER
----------------------------------------------------------------------------------------------------

  Força:
    • MOV como evento com custo médio; fluxo industrial MP↓ → sobra → PA↑.
    • Inventário + ajuste com SoD; REM como não-venda.
    • Item REVENDA separado do PED (não força OP fictícia).

  Risco residual: política de retalho mínimo = parâmetro ratificado.
  Caminho: estoque na virada (saldo de abertura) + MOV do dia 1; histórico depois.

----------------------------------------------------------------------------------------------------
2.5. M05 — FISCAL OPERACIONAL                                 NOTA: 9,5 | DECISÃO: MANTER
----------------------------------------------------------------------------------------------------

  Força:
    • Focus adapter; ERP não inventa numeração; idempotência de emissão.
    • NF ≠ fechamento oficial; faturamento parcial no mesmo PED.
    • Fronteira Contador cristalina.

  Risco residual: CFOP amostra/remessa/DEV com homologação do contador.
  Caminho: emitir só pós-homolog Focus (homolog ≠ prod).

----------------------------------------------------------------------------------------------------
2.6. M06 — FINANCEIRO                                         NOTA: 9,4 | DECISÃO: MANTER (+ §5.1)
----------------------------------------------------------------------------------------------------

  Força:
    • TIT verdade financeira; COB satélite; BX idempotente + fila ambígua.
    • Naturezas 1–5 obrigatórias; aging; régua WA oficial (S).
    • Adiantamento BX libera produção — fecha o loop com M02.

  Ponto de ownership: UC-FIN-010 (ENT) vive no pacote Financeiro nos UCs,
  mas no mapa de contexto ENT é pós-faturamento operacional. RESOLVIDO em §5.1.

----------------------------------------------------------------------------------------------------
2.7. M07 — COMPRAS                                            NOTA: 9,0 | DECISÃO: MANTER (FASE 2)
----------------------------------------------------------------------------------------------------

  Força: COT→OC→XML→MOV; urgência com alçada; OP parada por falta de material.
  Prioridade correta: todos S no índice — não bloqueiam o fluxo feliz de venda.
  Caminho: entrada XML cedo se útil à virada; cotação formal pode esperar.

----------------------------------------------------------------------------------------------------
2.8. M08 — PÓS-VENDA                                          NOTA: 9,3 | DECISÃO: MANTER (FASE 2)
----------------------------------------------------------------------------------------------------

  Força: RMA→CQ→decisão; DEV estorna fiscal+estoque+financeiro sem apagar origem.
  Caminho: 1 caso controlado em homologação antes de operar em massa.

----------------------------------------------------------------------------------------------------
2.9. M09 — INTEGRAÇÕES                                        NOTA: 9,6 | DECISÃO: MANTER
----------------------------------------------------------------------------------------------------

  Força: adapters (Focus, BankProvider, Meta); webhook idempotente; kill-switch;
         cadência/circuit breaker em API free.
  Caminho: contrato interno estável no dia 1 — trocar banco/hub sem reescrever TIT/NF.

----------------------------------------------------------------------------------------------------
2.10. M10 — GERENCIAL                                         NOTA: 9,1 | DECISÃO: MANTER
----------------------------------------------------------------------------------------------------

  Força: DRE interno ≠ contábil oficial; export contador Must; LAI proibido.
  Caminho: export mensal é Must de go-live; DRE/RH/patrimônio endurecem depois.

----------------------------------------------------------------------------------------------------
2.11. M11 — PLATAFORMA                                        NOTA: 9,5 | DECISÃO: MANTER (PRIMEIRO)
----------------------------------------------------------------------------------------------------

  Força: login individual, RBAC/SoD, empresa_id, auditoria, TAB versionado,
         anti-delete físico, feature flags.
  Caminho: implementar ANTES dos módulos de negócio profundos — sem isso o resto
           não é auditável nem multi-empresa de verdade.

4. DECISÃO DO CAMINHO — O QUE FAZER DAQUI PRA FRENTE
====================================================================================================

----------------------------------------------------------------------------------------------------
4.1. CAMINHO ESCOLHIDO (OFICIAL)
----------------------------------------------------------------------------------------------------

  NOME CURTO ......: “Monólito modular orientado a domínio (DDD pragmático)”
  CÓDIGO INTERNO ..: ADR-DOM-001 / CAMINHO-A

  Em uma frase:
    Um único deploy (API + workers), módulos internos = bounded contexts M01–M11,
    PED como raiz operacional, adapters para Focus/Banco/WhatsApp, PostgreSQL
    como verdade, filas para NF/COB/BX/MSG, sem microsserviços no dia 1.

  Por que este caminho (e não os outros):
    • Volume real (≤10 users, ≈200 NF) NÃO paga tax de microsserviço.
    • Domínio já está coeso — fronteiras lógicas bastam; não precisa rede entre módulos.
    • Equipe enxuta: um repositório, um pipeline, um banco, contratos claros.
    • Troca de banco/hub já resolvida por PORT/ADAPTER — sem precisar “explodir” o core.
    • Implantação por fases (Must FASE 1) já mapeada nos UCs.

----------------------------------------------------------------------------------------------------
4.2. CAMINHOS REJEITADOS (COM MOTIVO) — NÃO REABRIR
----------------------------------------------------------------------------------------------------

  CAMINHO-B — Microsserviços por módulo (Comercial, Fiscal, Fin…)
    REJEITADO. Consistência PED↔NF↔TIT↔MOV vira saga distribuída; custo AWS e
    complexidade operacionais incompatíveis com o porte. Extrair serviço só com
    motivo mensurável (hoje: nenhum).

  CAMINHO-C — Modularização fraca / “CRUD gigante sem agregado”
    REJEITADO. Quebra snapshot ORC→PED, mistura NF com TIT, abre porta a delete
    e float — exatamente o que os invariants proíbem.

  CAMINHO-D — DDD acadêmico completo (Event Storming weeks, CQRS/ES full)
    REJEITADO como abordagem inicial. O pacote já EXERCE linguagem ubíqua e
    eventos. Usar Event Sourcing total em estoque/financeiro agora atrasa go-live
    sem ganho. Preferir: estado atual no Postgres + event log / outbox quando
    precisar de integração e auditoria.

  CAMINHO-E — ERP genérico white-label / customização infinita
    REJEITADO. Domínio RLP é flexo (bobina, sobra, FAC, gordura, REM). Customização
    sem limite destrói o baseline. Feature flags por fase — não product builder.

  CAMINHO-F — Reabrir LAI / livro paralelo “só gerencial”
    REJEITADO DEFINITIVAMENTE. Contamina oficial. Ver DECISAO_NAO_IMPLEMENTAR_LAI.

----------------------------------------------------------------------------------------------------
4.3. ESTILO DE CÓDIGO DO DOMÍNIO (DDD PRAGMÁTICO — OBRIGATÓRIO)
----------------------------------------------------------------------------------------------------

  Adotar:
    • Aggregates com invariantes no domínio (não só na UI)
    • Application services / use-cases (mapear 1 UC-xxx ≈ 1 comando ou fluxo)
    • Domain events (catálogo DOMINIO §11) publicados via outbox quando cruzam módulo
    • Ports & Adapters nas bordas (Focus, BankProvider, WhatsApp, storage)
    • DECIMAL / tipos monetários fortes — zero float binário
    • Id BIGINT (PK) + codigo legível (único por empresa quando fizer sentido)
    • Soft-delete / estorno — nunca DELETE físico de documento operacional

  Não adotar no dia 1:
    • Event Sourcing como store principal
    • Saga orquestrada multi-serviço
    • GraphQL obrigatório
    • “Shared Kernel” inchado entre todos os módulos (só EmpresaId, Money, Audit)

4.4. ORDEM DE IMPLEMENTAÇÃO DECIDIDA (BLOQUEANTE)
----------------------------------------------------------------------------------------------------

  Fase 0 — Fundação (M11 + infra)
    Auth, RBAC/SoD, empresa_id, auditoria, TAB, filas, S3, OpenAPI, decimal utils.

  Fase 1 — Virada operacional (Must)
    M01 Cadastros → M02 ORC/PED/CRT → M04 estoque dia-1 → M03 OP/OS básicas
    → M05 NF Focus → M06 TIT/COB/BX + ENT → M09 adapters Must → M10 export contador.

  Fase 2 — Endurecimento (Should)
    Compras COT/OC, RMA/DEV, régua WA, comissão, frete, REM, manutenção, amostragem,
    BankProvider prod (Sicoob), WABA templates oficiais.

  Fase 3 — Expansão controlada (Could)
    EMP-00002 se Contador+Direção aprovarem; CT-e/API frete; Lucro Real prep
    (GER-006); assinatura canhoto.

  Regra: NÃO iniciar Fase 2 “bonita” se Fase 1 não fecha CA do SRS §15.2.

5. REFINAMENTOS MÍNIMOS DE OWNERSHIP (FECHADOS NESTE TXT)
====================================================================================================

  Estes NÃO mudam o domínio de negócio — só eliminam dúvida de pacote/módulo
  na hora de escrever código e pastas.

----------------------------------------------------------------------------------------------------
5.1. ENTREGA (ENT) — ownership canônico
----------------------------------------------------------------------------------------------------

  DECISÃO:
    • Conceito de domínio ENT pertence à cadeia pós-faturamento (romaneio /
      confirmação cliente / transição PED → ENTREGUE).
    • Pacote de CASOS DE USO pode permanecer UC-FIN-010 por histórico do índice
      (não renumerar agora — custo > benefício).
    • No CÓDIGO: módulo/pasta preferencial `expedicao` OU `logistica`, NÃO
      misturar regra de romaneio dentro do agregado Título.
    • Dependências: ENT consulta PED + NF (política “NF antes de expedir”);
      dispara evento EntregaConfirmada; Financeiro só observa (aging/status).

  Proibido:
    • Fazer de TIT o dono do romaneio.
    • Permitir ENT total sem NF quando parâmetro NF-antes-expedir = SIM.

----------------------------------------------------------------------------------------------------
5.2. BEM PATRIMONIAL — ownership canônico
----------------------------------------------------------------------------------------------------

  DECISÃO:
    • Cadastro/capitalização/valor mínimo = Gerencial/Patrimônio (M10 / UC-GER-002).
    • Plano preventivo operacional = Produção (M03 / UC-PRD-006) referenciando
      bem_id — não duplicar entidade.
    • Uma tabela/agregado BEM; dois casos de uso; zero “máquina paralela”.

----------------------------------------------------------------------------------------------------
5.3. CRÉDITO (CRT)
----------------------------------------------------------------------------------------------------

  DECISÃO já implícita e agora explícita:
    • Limite e liberação = responsabilidade FINANCEIRO (comandos em financeiro/crédito).
    • Comercial só CONSULTA (UC-COM-007) — nunca altera limite.
    • UC-COM-008 permanece no pacote Comercial do índice por encadeamento ORC→PED,
      mas o agregado/serviço de escrita é Financeiro.

----------------------------------------------------------------------------------------------------
5.4. COMISSÃO / FRETE
----------------------------------------------------------------------------------------------------

  DECISÃO:
    • Conceitos financeiros (COM, frete receita×despesa) no Financeiro.
    • Frete fase 2 CT-e continua FORA (DOMÍNIO §12) — só registro gerencial agora.

6. CHECKLIST “MODELO EXCELENTE → CÓDIGO SEM REGREDIR”
====================================================================================================

  Antes de mergear qualquer feature de domínio, a PR deve passar:

  [ ] Nomes iguais ao glossário (ORC/PED/OP/OS/MOV/NF/TIT/COB/BX/ENT/RMA/DEV…)
  [ ] Relacionamentos por id BIGINT; código só exibição/busca
  [ ] empresa_id presente; isolamento EMP-00002 venda off
  [ ] Sem float em dinheiro/qtde/alíquota/custo
  [ ] Sem delete físico de documento; estorno/compensação
  [ ] Dinheiro/NF com chave de idempotência
  [ ] NF e TIT criados como conceitos distintos no faturamento
  [ ] Produção só após CRT OK ou BX de adiantamento
  [ ] Aceite PED só via link formal (nunca “combinado no zap”)
  [ ] Snapshot ORC aprovado não recalcula preço no PED
  [ ] Natureza 1–5; grupo 9 / LAI impossível
  [ ] Adapter nas bordas Focus / Bank / WhatsApp
  [ ] Auditoria quem/quando/de→para em ações críticas
  [ ] UC Must da Fase 1 tem teste de aceite mapeável

  Se um item falhar → não é “dívida técnica aceitável”; é regressão de domínio.
