1. PREMISSA IMPORTANTE: A IE NAO NASCE NA RECEITA FEDERAL
================================================================================

A Inscricao Estadual e um cadastro ESTADUAL, ligado ao ICMS.
Quem concede e mantem a IE e a Secretaria da Fazenda (SEFAZ) de cada UF
(26 estados + DF).

Portanto:
  - Receita Federal (base CNPJ)  -> identifica empresa federalmente
  - SEFAZ / Sintegra / CCC       -> informam IE, situacao estadual, tipo etc.

Uma API "de Inscricao Estadual" NAO inventa o numero. Ela apenas:
  1) recebe CNPJ (e/ou UF)
  2) consulta as FONTES OFICIAIS estaduais (ou o CCC)
  3) normaliza a resposta em JSON
  4) devolve ao cliente, cobrando credito/cota

Empresas como SintegrAPI, FiscalAPI, Infosimples, dbdireto etc. sao
AGREGADORES / PROXY inteligentes — nao sao a fonte primaria.


================================================================================
2. DE ONDE O SISTEMA OBTEM AS INSCRICOES ESTADUAIS
================================================================================

Na pratica, um produto desse tipo combina 2 grandes fontes:


--------------------------------------------------------------------------------
2.1. FONTE A — Cadastro Centralizado de Contribuintes (CCC)
--------------------------------------------------------------------------------

O que e:
  Base nacional mantida no ambito do Sintegra / SEFAZs para credenciamento
  de emitentes de documentos fiscais eletronicos (NF-e etc.) e validacao
  de destinatario em operacoes internas e interestaduais.

O que geralmente informa:
  - vinculo CNPJ <-> Inscricao Estadual
  - situacao do contribuinte na SEFAZ
  - habilitacao para operar / emitir
  - historico / dados cadastrais (conforme disponibilidade)

Consulta publica (portal conhecido):
  https://dfe-portal.svrs.rs.gov.br/NFE/CCC
  (ambiente DFe / SVRS — Receita Estadual RS hospeda a consulta nacional)

Fluxo tipico no portal:
  1) escolher a UF
  2) informar CNPJ, CPF ou IE
  3) pesquisar
  4) ver se existe IE vinculada e situacao

Uso no seu sistema:
  Worker automatizado que consulta o CCC por UF+CNPJ e extrai o resultado.
  Util especialmente para descobrir se ha IE naquela UF e o vinculo basico.

Limitacoes:
  - Nem sempre traz o mesmo nivel de detalhe de um Sintegra estadual
  - Layout/campos podem variar; dependencia do portal nacional
  - Algumas UFs / dados mais ricos exigem certificado digital ou acesso
    autenticado a webservices oficiais (quando existem)


--------------------------------------------------------------------------------
2.2. FONTE B — Portais Sintegra / Cadastro de Contribuintes de cada SEFAZ
--------------------------------------------------------------------------------

O que e:
  Cada UF tem (ou teve) um portal de consulta cadastral de contribuintes
  de ICMS — frequentemente chamado de "Consulta Sintegra", "Cadastro de
  Contribuintes", "Consulta IE" etc.

Exemplos de ideias (URLs mudam com o tempo; sempre validar na SEFAZ):
  - consulta por CNPJ/IE no portal da SEFAZ-SP, SEFAZ-MG, SEFAZ-RJ...
  - cada estado com HTML, captcha, sessao e campos DIFERENTES

O que pode retornar (varia por UF):
  - numero da IE
  - razao social
  - situacao (ativa, baixa, suspensa...)
  - tipo de IE (normal, ST, produtor rural, nao contribuinte...)
  - endereco do estabelecimento
  - CNAE, regime, datas etc. (quando a UF publica)

Uso no seu sistema:
  Um "conector" / worker POR UF:
    - monta a requisicao no formato daquele portal
    - resolve proteção antibot (quando legal e necessario)
    - faz parse do HTML/JSON retornado
    - mapeia para um modelo interno padrao

Por que e dificil:
  - 27 portais diferentes = 27 manutencoes distintas
  - captcha, rate-limit, mudanca de layout frequente
  - instabilidade: SEFAZ fora do ar, lentidao, mudanca de URL
  - juridico/ToS: scraping em massa deve respeitar termos, LGPD e uso aceitavel


--------------------------------------------------------------------------------
2.3. FONTES AUXILIARES (nao substituem SEFAZ, mas ajudam o fluxo)
--------------------------------------------------------------------------------

  Receita Federal (CNPJ)
    - descobre UF da matriz/filial, razao social, situacao federal
    - NAO substitui a IE; serve para sugerir qual UF consultar primeiro

  Bases privadas / cache proprio
    - o agregador guarda resultados de consultas anteriores (cache)
    - melhora velocidade e disponibilidade quando a SEFAZ cai
    - e exatamente o que a SintegrAPI chama de cache_strategy

  Webservices oficiais (quando a UF oferece)
    - alguns estados / SVRS disponibilizam servicos autenticados
      (certificado digital A1/A3) para validacao cadastral em fluxo fiscal
    - mais estavel que HTML, mas acesso e mais restrito (geralmente
      empresas com necessidade fiscal / certificado)

3. VISÃO GERAL: O QUE UM "SINTEGRAPI-LIKE" REALMENTE FAZ
================================================================================

Cliente            Sua API              Fontes oficiais
-------            -------              ---------------
App/ERP  --HTTP--> Gateway/API  -------> CCC (SVRS)
                     |                  SEFAZ-SP Sintegra
                     |                  SEFAZ-MG ...
                     |                  SEFAZ-... (27 UFs)
                     v
                   Cache Redis/DB
                     |
                     v
                   JSON padronizado
                   (inscricoes_estaduais[])


O valor do produto NAO e "ter a base secreta da IE".
O valor e:
  - unificar 27 portais em 1 endpoint
  - lidar com falha/captcha/lentidao
  - cache inteligente
  - resposta estavel em JSON
  - cobranca por credito / plano


================================================================================
4. ARQUITETURA SUGERIDA (DO ZERO)
================================================================================

Componentes minimos:


(1) API Gateway / Backend REST
    - autenticacao por API key (x-api-key)
    - endpoint: GET /consultas/sintegra/{cnpj}?uf=SP|BR
    - validacao de CNPJ, controle de cota/creditos
    - enfileira jobs quando uf=BR (consulta paralela)

(2) Orquestrador de consultas
    - decide: cache hit? CCC? portal estadual?
    - aplica estrategia: ONLINE_PREFERENCIAL, CACHE_*, etc.
    - timeout, retry, circuit breaker por UF

(3) Workers / conectores por fonte
    - worker_ccc
    - worker_sefaz_sp, worker_sefaz_mg, ... (ou plugins por UF)
    - cada um devolve um DTO interno padrao:

        {
          "cnpj": "...",
          "uf": "SP",
          "inscricao_estadual": "...",
          "ativa": true,
          "tipo_ie": "...",
          "situacao_pj": "...",
          "endereco": {...} | null,
          "fonte": "ccc|sintegra_sp|...",
          "consultado_em": "ISO-8601"
        }

(4) Camada de normalizacao
    - traduz "Habilitado"/"Ativo"/"Sem restricao" de cada UF
      para campos padrao (ativa, situacao_pj, tipo_ie)
    - trata multiplas IEs no mesmo CNPJ (empresa ST em outras UFs)

(5) Cache
    - chave tipica: cnpj + uf (+ tipo consulta)
    - TTL configuravel (ex.: 7 dias)
    - flag is_cache na resposta
    - fallback quando fonte oficial falha

(6) Persistencia e billing
    - usuarios, api_keys, planos, consumo mensal
    - log de request_id para auditoria
    - contador: 1 credito por UF consultada; +1 se endereco etc.

(7) Observabilidade
    - taxa de sucesso por UF
    - latencia p50/p95
    - alerta quando um conector quebra (SEFAZ mudou o HTML)


Fluxo resumido (uf=SP):

  1. Cliente chama GET /sintegra/CNPJ?uf=SP
  2. API valida key e credito
  3. Orquestrador olha cache (conforme estrategia)
  4. Se precisa online:
       a) tenta CCC com UF=SP  e/ou
       b) tenta conector Sintegra/SEFAZ-SP
  5. Normaliza resultado -> grava cache -> debitar credito
  6. Retorna JSON

Fluxo uf=BR:

  1. Cliente chama com uf=BR
  2. Orquestrador dispara N jobs (uma UF por vez / em paralelo limitado)
  3. Agrega todas as IEs encontradas
  4. Cobrar 1 credito por UF efetivamente consultada
  5. Retornar lista inscricoes_estaduais[]

5. STACK TECNICA TIPICA (EXEMPLO)
================================================================================

  Backend API ....... Node/Nest, Python/FastAPI, Go, Java etc.
  Fila .............. Redis Queue / RabbitMQ / SQS (jobs por UF)
  Cache ............. Redis
  Banco ............. PostgreSQL (usuarios, logs, billing, IEs cacheadas)
  Workers ........... containers isolados por grupo de UFs
  Proxy/IP pool ..... se volume alto (portais bloqueiam IP)
  Captcha solver .... servico terceirizado (custo relevante) quando o portal exige
  Certificado ....... A1 em HSM/safe storage se usar webservice autenticado
  Deploy ............ Kubernetes / Cloud Run / VMs
  Front dashboard ... planos, chave API, consumo (como a SintegrAPI tem)


================================================================================
6. DESAFIOS REAIS (POR QUE ESSE NEGOCIO EXISTE)
================================================================================

1) Fragmentacao
   27 fontes, layouts e regras diferentes. Manutencao continua.

2) Instabilidade das SEFAZs
   Portais caem, mudam URL, colocam captcha novo. Sem cache + fallback,
   sua API "quebra" junto.

3) Custo operacional
   Proxies, captcha, retries e equipe de manutencao dos conectores
   pesam mais que o codigo da API REST em si.

4) Consistencia dos dados
   Mesmo CNPJ pode ter:
     - IE na UF sede
     - IE de substituto tributario em outras UFs
     - IE de canteiro / nao contribuinte
   O agregador precisa listar todas sem "inventar".

5) Compliance (LGPD / ToS / uso aceitavel)
   Dados cadastrais publicos ainda exigem finalidade clara, logs,
   seguranca da API key e politicas de privacidade.
   Evitar abuso (bombardeio de portais) — risco de bloqueio e juridico.

6) Nao ha dump oficial completo e gratuito "de todas as IEs do Brasil"
   atualizado em tempo real para baixar e servir.
   O negocio e consultar sob demanda nas fontes + cache.


================================================================================
7. CAMINHO PRAGMATICO PARA CONSTRUIR (FASES)
================================================================================

FASE 0 — Entender o problema
  Consultar manualmente CCC e 2-3 Sintegras (ex.: SP, MG, RS).
  Anotar campos retornados e diferencas.

FASE 1 — MVP de 1 UF
  API simples + conector de 1 estado (ou so CCC com UF fixa).
  Cache Redis + resposta JSON padrao.
  Auth por API key.

FASE 2 — CCC + poucas UFs estrategicas
  Expandir conectores SP, MG, RJ, PR, RS (maior volume de mercado).
  Normalizador de situacao/tipo_ie.

FASE 3 — Cobertura nacional
  27 conectores OU estrategia hibrida:
    - CCC para descoberta ampla
    - portal estadual para detalhe/endereco quando pedido
  Orquestracao uf=BR com fila.

FASE 4 — Produto comercial
  Planos, billing, dashboard, SLA, alertas de conector quebrado,
  documentacao OpenAPI, status page.

Alternativa comum de negocio:
  Em vez de construir os 27 conectores, REVENDA / Integre uma API
  pronta (SintegrAPI etc.) e foque no seu produto de negocio
  (ERP, cadastro, antifraude). Muitas vezes e mais barato e estavel.


================================================================================
8. O QUE NAO FAZER
================================================================================

- Nao "fabricar" IE a partir do CNPJ com formula inventada
  (existem algorimos de digito verificador POR UF, mas isso so VALIDA
   formato; nao prova existencia/situacao no cadastro oficial).

- Nao assumir que a base CNPJ da Receita contem IE completa.
  IE e dominio estadual.

- Nao depender de um unico IP/scraping fragil sem monitoramento:
  amanha a SEFAZ muda 1 campo e seu produto para.


================================================================================
9. RESUMO EM UMA FRASE
================================================================================

Um sistema como o da SintegrAPI obtem as Inscricoes Estaduais CONSULTANDO
em tempo (quase) real as fontes oficiais — principalmente o CCC
(Cadastro Centralizado de Contribuintes) e os portais/cadastros das
SEFAZs/Sintegra de cada UF —, guarda em cache, normaliza em JSON e
vende isso como API com plano/creditos.

Ele nao e a SEFAZ: e uma camada de integracao sobre as SEFAZs.
