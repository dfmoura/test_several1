====================================================================================================
0. ESSÊNCIA DO DOMÍNIO
====================================================================================================

  A RLP é indústria de etiquetas autoadesivas. O domínio do ERP cobre a
  cadeia operacional completa:

    ORÇAR → PEDIR → PRODUZIR/SEPARAR → FATURAR → ENTREGAR → RECEBER

  com exceções (RMA/DEV), compras, remessa industrial, gerencial interno
  e export disciplinado ao contador.

  PEDIDO (PED) é o documento-mestre. Todo o resto (OP, OS, NF, TIT, COB,
  ENT, BX, RMA, DEV, COM…) aponta para o PED ou para cadastros mestres —
  nunca inventa um “pedido paralelo” em outro sistema.

  Fronteira explícita do domínio ERP:
    DENTRO ........ operação, estoque, crédito interno, NF via hub, títulos,
                    cobrança, entrega, DRE gerencial, export ao contador.
    FORA .......... apuração fiscal oficial, SPED, eSocial completo, LAI /
                    caixa 2, CT-e/API transportadora (fase 2).

====================================================================================================
1. REGRAS DE OURO DO DOMÍNIO (INVARIANTS)
====================================================================================================

  D0.1  Um único ERP. PED é o agregado-raiz operacional da venda.
  D0.2  Produção, estoque, NF, título, cobrança, entrega e baixa vivem no
        mesmo bounded system — não viram satélites.
  D0.3  Contábil, fiscal e folha OFICIAIS ficam com o CONTADOR.
        O ERP alimenta; NÃO fecha apuração fiscal.
  D0.4  Documento não se apaga — estorna/compensa com trilha auditável.
  D0.5  Identidade em duas camadas: id BIGINT (motor) + codigo legível
        (negócio). Relacionamentos SEMPRE por id.
  D0.6  Integrações por adapter: Focus NFe, BankProvider, WhatsApp Meta.
  D0.7  Multi-empresa por empresa_id (default EMP-00001). Credenciais isoladas.
  D0.8  LAI / livro paralelo / “caixa 2” NÃO existe no domínio.
  D0.9  WhatsApp oficial somente via API Meta (nunca conta pessoal).
  D0.10 Dinheiro e NF são IDEMPOTENTES (webhook, job, retry).
  D0.11 Proibido ponto flutuante binário para dinheiro, qtde, alíquota, custo.
  D0.12 Exceção (RMA/DEV) complementa o fluxo feliz — não o apaga.
  D0.13 Aceite formal de ORC (link). “Combinado no zap” NÃO gera PED.
  D0.14 Snapshot do ORC aprovado trava o PED (preço/spec/qtde/prazo/condição).
  D0.15 Liberação de produção exige crédito OK ou adiantamento baixado (BX).
  D0.16 Documento fiscal ≠ título financeiro — nascem juntos no faturamento,
        mas são conceitos distintos.
  D0.17 Naturezas gerenciais só grupos 1–5. Grupo 9.xx / LAI proibidos.

3. BOUNDED CONTEXTS (MÓDULOS DE DOMÍNIO)
====================================================================================================

  Contexto               Código   Responsabilidade principal
  ---------------------  -------  ------------------------------------------------
  Cadastros              M01      PAR, produtos, usuários, perfis, parâmetros
  Comercial              M02      ORC (versão, cenário, gordura, crédito) → PED
  Produção / PCP         M03      OP, OS, apontamento, conclusão, BEM preventivo
  Estoque                M04      MOV, inventário, sobra/retalho, REM
  Fiscal operacional     M05      NF-e/NFS-e via Focus; metadados; sem fechamento
  Financeiro             M06      TIT, COB, BX, aging, crédito, naturezas, contas
  Compras                M07      COT, OC, urgência, entrada XML
  Pós-venda              M08      RMA, DEV, garantia, amostra/protótipo
  Integrações            M09      BankProvider, WhatsApp MSG, Focus, jobs cadência
  Gerencial              M10      DRE interno, patrimônio, RH pagamento, export
  Plataforma             M11      auth, auditoria, filas, arquivos, multi-empresa

  Regra de dependência:
    Contextos operacionais CONVERGEM no PED (mestre).
    Produção CONSULTA o PED; não cria “sistema de produção” paralelo.
    Fiscal operacional e Financeiro nascem juntos no faturamento, mas
    permanecem agregados distintos (NF ≠ TIT).

4. AGREGADOS E ENTIDADES CENTRAIS
====================================================================================================

  Convenção de modelagem:
    • Agregado = fronteira de consistência; muda por comandos/eventos.
    • Entidade = identidade estável (id + codigo).
    • Filho = só existe no contexto do agregador.
    • Relacionamentos entre agregados = por id BIGINT.

----------------------------------------------------------------------------------------------------
4.1. CADASTROS (M01)
----------------------------------------------------------------------------------------------------

  Empresa (EMP)
    Atributos-chave: cnpj, razao_social, flags (venda_ativa, estoque_ativo),
                     regime, parâmetros fiscais por empresa_id.
    Invariants: EMP-00002 sem venda/estoque até homologação Contador+Direção.
                Credenciais Focus/banco isoladas por empresa.

  Parceiro (PAR)  [agregado]
    Papéis: CLIENTE | FORNECEDOR | TRANSPORTADORA | COLABORADOR | OUTRO
            (mesmo PAR pode ter múltiplos papéis).
    Filhos: endereços, contatos, dados bancários (SoD: só FINANCEIRO+alçada),
            papéis, indIEDest / IE.
    Invariants: prospect pode orçar sem fiscal completo; PED exige cadastro
                completo (+ sinal se exigido). CNPJ/CPF único quando informado.

  Produto / SKU  [agregado]
    Famílias compra: MP | EMB | REV
    Famílias venda:  PA | REV | SVC
    Filhos/attrs: NCM, CFOP padrão, CST/CSOSN, unidades, fatores conversão,
                  máscara estruturada (bobina), custo médio.
    Relacionados: FAC (ferramental) quando aplicável ao pedido.

  Usuário (USR) / Perfil (PER)
    Login = e-mail corporativo individual, intransferível.
    Autorização = só via PER (RBAC). Soft-delete / inativação.

  Parâmetro (TAB)
    Valores oficiais versionados; não ratificados = PENDENTE_RATIFICACAO.

----------------------------------------------------------------------------------------------------
4.2. COMERCIAL (M02)
----------------------------------------------------------------------------------------------------

  Orçamento (ORC)  [agregado]
    Identidade: ano + numero + versao (código ORC-AAAA-NNNNN + versão).
    Filhos: itens (spec, preço, prazo, tolerância), cenários de simulação,
            condições de pagamento, frete, impostos estimados, gordura.
    Relaciona: PAR (cliente/prospect), CRT (consulta limite).
    Invariants:
      • Versionamento: cenário não destrói versão base.
      • Imposto no ORC é estimativa/gross-up; divergência pós-NF é analisada.
      • Desconto/customização respeitam alçadas.
      • Aceite formal via LINK gera PED; zap informal não gera.

  Pedido (PED)  [agregado-raiz operacional]
    Snapshot travado do ORC aprovado (preço/spec/qtde/prazo/condição).
    Filhos: itens tipados PRODUCAO | SERVICO | REVENDA.
    Relaciona: PAR, ORC origem, CRT/liberação, adiantamentos (TIT/COB/BX).
    Invariants:
      • Não recalcular preço na conversão ORC→PED.
      • Produção só após crédito OK ou adiantamento com BX.
      • Recorrência/lembrete gera NOVO ciclo ORC→aceite; nunca PED sozinho.

  Crédito / Liberação (CRT)
    Limite do cliente; liberação financeira.
    Invariant: comercial NÃO altera limite (SoD).

----------------------------------------------------------------------------------------------------
4.3. PRODUÇÃO / PCP (M03)
----------------------------------------------------------------------------------------------------

  Ordem de Produção (OP)  [agregado]
    Nasce de item PRODUCAO do PED.
    Filhos: apontamentos, consumo MP, sobra, retorno PA, CQ amostragem.
    Estados: ABERTA → EM_ANDAMENTO → CONCLUIDA | CANCELADA.
    Invariant: conclusão libera PA e permite política de faturamento.

  Ordem de Serviço (OS)  [agregado]
    Nasce de item SERVICO do PED. Conclusão encerra o item.

  Bem / Manutenção (BEM)
    Ativo patrimonial + plano preventivo amarrado à máquina.

  Qualidade / Amostra / Protótipo
    Conceitos auxiliares: amostragem, certificado, contra-prova;
    amostra/protótipo com política de custo e NF (parecer contador).

----------------------------------------------------------------------------------------------------
4.4. ESTOQUE (M04)
----------------------------------------------------------------------------------------------------

  Movimento (MOV)  [entidade de evento]
    Tipos: entrada, saída, transferência, retorno, industrialização.
    Sempre com custo médio; nunca “some” saldo sem documento.

  Fluxo industrial típico:
    saída MP → registro sobra/retalho → retorno PA

  Inventário (INV) / Ajuste (AJU)
    Contagem e correção com aprovação segregada (SoD).

  Remessa de industrialização (REM)
    Envio a terceiro com prazo e retorno; não confundir com venda.

  Lote (LOT)
    Rastreio quando a operação exigir.

----------------------------------------------------------------------------------------------------
4.5. FISCAL OPERACIONAL (M05)
----------------------------------------------------------------------------------------------------

  DocumentoFiscal (NF-e / NFS-e)  [agregado operacional]
    Numeração: SEFAZ/Focus — ERP NÃO inventa número.
    Guarda: série, número, chave44, XML/PDF, vínculo ped_id, empresa_id.
    Operações: emissão, consulta, cancelamento, carta de correção (API).
    Invariants:
      • Idempotência na emissão (retry não duplica).
      • Não é fechamento SPED / apuração oficial.
      • Faturamento parcial amarrado ao mesmo PED permitido.

----------------------------------------------------------------------------------------------------
4.6. FINANCEIRO (M06)
----------------------------------------------------------------------------------------------------

  Título (TIT)  [agregado — verdade financeira]
    A receber ou a pagar; natureza gerencial obrigatória (1–5).
    Estados: ABERTO → COBRADO → PARCIALMENTE_BAIXADO → BAIXADO | PERDA | CANCELADO

  Cobrança (COB)
    Emissão bancária vinculada ao TIT (não substitui o TIT).
    Estados: PENDENTE → REGISTRADA → PAGA | CANCELADA | VENCIDA

  Baixa (BX)
    Quitação por webhook / extrato / CNAB; ambiguidade → fila humana.
    Invariant: idempotente (não duplicar BX).

  Conta financeira / Aging / Régua
    Contas caixa/banco; aging; régua D-3, D+1, D+7, D+15 via templates WA.

  Frete (conceito financeiro)
    Receita × despesa + avaria; transportadora = PAR com papel.

  Comissão (COM)
    Base FATURADO | RECEBIDO (a ratificar); nunca planilha/zap.

----------------------------------------------------------------------------------------------------
4.7. COMPRAS (M07)
----------------------------------------------------------------------------------------------------

  Cotação (COT) → Ordem de Compra (OC)
  Urgência com alçada; OP pode ficar parada por falta de material.
  Entrada XML via Focus + manifestação + conferência → MOV entrada.

----------------------------------------------------------------------------------------------------
4.8. PÓS-VENDA (M08)
----------------------------------------------------------------------------------------------------

  RMA  [agregado]
    Reclamação → CQ → decisão (reparo | reposição | crédito | DEV).
    Estados: ABERTA → EM_CQ → DECIDIDA → ENCERRADA

  Devolução (DEV)  [agregado]
    Estorno ponta a ponta: fiscal + estoque + financeiro.
    Estados: ABERTA → FISCAL_OK → ESTOQUE_OK → FINANCEIRO_OK → ENCERRADA
    Invariant: documentos compensatórios ligados à origem; origem permanece.

----------------------------------------------------------------------------------------------------
4.9. GERENCIAL (M10)
----------------------------------------------------------------------------------------------------

  Natureza (NAT)
    Árvore 1–5 (receitas, custos, despesas, investimentos, não-resultado).
    De-para homologado para o plano do contador.

  DRE / Caixa interno
    Visão gerencial RLP a partir das naturezas — não é contabilidade oficial.

  Patrimônio (BEM)
    Capitalização com valor mínimo parametrizado.

  RH pagamento gerencial
    Pagamento + vínculo colaborador; sem fechar eSocial.

  Export Contador
    Pacote mensal + layout import de folha.

    ABERTA → EM_ANDAMENTO → CONCLUIDA
                          → CANCELADA

  TIT:
    ABERTO → COBRADO → PARCIALMENTE_BAIXADO → BAIXADO
                                           → PERDA
                                           → CANCELADO

  COB:
    PENDENTE → REGISTRADA → PAGA
                          → CANCELADA
                          → VENCIDA

  RMA:
    ABERTA → EM_CQ → DECIDIDA → ENCERRADA

  DEV:
    ABERTA → FISCAL_OK → ESTOQUE_OK → FINANCEIRO_OK → ENCERRADA

  Transições inválidas = erro de domínio (não “forçar no banco”).
  Detalhe fino de eventos: TXT de cada fluxo.

====================================================================================================
7. FLUXOS DE DOMÍNIO
====================================================================================================

----------------------------------------------------------------------------------------------------
7.1. FLUXO FELIZ (cadeia principal)
----------------------------------------------------------------------------------------------------

  1. Comercial cria ORC (versão, itens, imposto estimado, gordura).
  2. Cliente ACEITA via link formal.
  3. Sistema gera PED com snapshot travado.
  4. FINANCEIRO libera crédito (CRT) OU baixa adiantamento (BX).
  5. PED → LIBERADO.
  6. Por tipo de item:
       PRODUCAO → OP → MOV (MP↓ / sobra / PA↑) → conclusão
       SERVICO  → OS → conclusão
       REVENDA  → separação (MOV REV↓)
  7. Faturamento: NF (Focus) + TIT + COB (política: NF antes de expedir).
  8. ENT (romaneio) + confirmação cliente + MSG status.
  9. BX via webhook/extrato/CNAB → crédito/caixa.

----------------------------------------------------------------------------------------------------
7.2. FLUXOS PARALELOS
----------------------------------------------------------------------------------------------------

  COT → OC → entrada XML → MOV compra
  REM (industrialização externa) com prazo/retorno
  COM (comissão) sobre faturado/recebido
  BEM preventivo (manutenção)
  INV / AJU (inventário e ajuste)

----------------------------------------------------------------------------------------------------
7.3. FLUXOS DE EXCEÇÃO
----------------------------------------------------------------------------------------------------

  RMA → CQ → (reparo | reposição | crédito comercial | DEV)
  DEV → estorno fiscal + estoque + financeiro (origem preservada)
  Estorno silencioso = proibido no domínio

9. ATORES E RESPONSABILIDADES NO DOMÍNIO
====================================================================================================

  Internos:
    ADMIN ........ parâmetros, usuários, exceções de sistema
    FISCAL ....... cadastro fiscal, emissão NF, metadados fiscais
    FINANCEIRO ... crédito, contas, TIT/COB/BX, liberação pagamentos

    PRODUCAO ..... OP/OS, apontamento, estoque de fábrica
    COMPRAS ...... COT/OC, fornecedor, XML entrada
    EXPEDICAO .... ENT / romaneio (opcional)
    CONSULTA ..... leitura

  Externos:
    Cliente ........... aceite de ORC (link), confirmação de entrega
    Contador .......... recebe export; fecha fiscal/contábil/folha
    Focus NFe ......... emissão/consulta NF
    Banco ............. Inter (sandbox) / Sicoob (prod) via BankProvider
    Meta WhatsApp ..... templates oficiais (MSG)
    Transportadora .... fase 2 (CT-e/API)

  Pares SoD (incompatíveis no mesmo ator, sem controle compensatório):
    • alterar dados bancários do favorecido × liberar pagamento
    • alterar limite de crédito × operar pedido comercial
    • ajustar estoque × aprovar inventário
    (matriz completa: ORGANIZACAO_USUARIOS_PERFIS_ACESSO.txt)

10. VALORES, UNIDADES E PRECISÃO (DOMÍNIO NUMÉRICO)
====================================================================================================

  Tipos de valor de negócio (nunca float binário):
    • Monetário final .................... 2 casas
    • Preço / custo unitário ............. 6 casas
    • Preço unitário NF (vUnCom) ......... até 10 casas
    • Quantidade estoque ................. 4 casas

  Unidades oficiais típicas: m, kg, rolo, un (+ fatores de conversão).
  Custo médio: recalculado nos MOV — domínio de Estoque + Financeiro gerencial.
  JSON decimal = STRING na fronteira de API.
  Trace: PADRAO_DECIMAL_CALCULOS.txt · CONVERSOES_UNIDADES_MEDIDA.txt

12. O QUE NÃO É DOMÍNIO DESTE ERP
====================================================================================================

  Explicitamente fora:
    • Apuração/fechamento fiscal oficial (SPED, obrigação principal)
    • Folha oficial completa / eSocial (só pagamento gerencial + import/export)
    • LAI / livro auxiliar / caixa 2
    • Venda em EMP-00002 sem parecer Contador + Direção
    • CT-e / API transportadora (FRETE Fase 2)
    • Assinatura eletrônica de canhoto (pós go-live opcional)
    • Marketplace público / app aberto a clientes em massa
