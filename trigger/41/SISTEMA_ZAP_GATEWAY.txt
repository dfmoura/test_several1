1. PROBLEMA QUE ESTE SISTEMA RESOLVE
--------------------------------------------------------------------------------
O sistema #25 é um agente que RECEBE mensagem no WhatsApp e responde com IA.

Este sistema (#41) é o inverso operacional:

  Sistema externo X  --POST-->  Zap Gateway  --> Fila  --> Worker
       --> Canal WhatsApp VINCULADO  --> Destinatário

É um GATEWAY DE ENVIO MULTI-TENANT POR CELULAR:
- Cada celular/WhatsApp cadastrado é um "Sender" isolado.
- O POST não escolhe "qualquer Zap genérico": ele fala com um cadastro específico
  (sender_id / api_key daquele vínculo).
- Trocar o número físico (novo aparelho / novo WhatsApp) é operação de vínculo
  no cadastro; o contrato do Sistema X permanece o mesmo (mesmo sender_id).


2. OBJETIVOS DE PRODUTO
--------------------------------------------------------------------------------
[Must]
- Aceitar POST autenticado com payload completo da mensagem.
- Enfileirar com resposta rápida (202 Accepted).
- Processar a fila e enviar via Evolution API (mesmo stack consolidado no #25).
- Isolar totalmente os enviadores (creds, sessão, fila lógica, rate limit).
- Permitir rebind do celular sem quebrar integradores.

[Should]
- Idempotência por (sender_id + external_id).
- Retentativas com backoff + DLQ (dead-letter).
- Status de entrega consultável (queued / processing / sent / failed / dead).
- Painel admin mínimo (senders, QR, fila, falhas).

[Could — fase 2]
- Templates / mídia / documentos.
- Webhook de callback para o Sistema X (status sent/failed).
- Escala horizontal de workers por fila.

5. MODELO DE SEGREGAÇÃO DOS ENVIADORES (CRÍTICO)
--------------------------------------------------------------------------------
Princípio: "um cadastro = um celular = uma identidade de API = uma fila lógica".

5.1 Entidade SENDER (cadastro do zap)
  - id (UUID)
  - name (rótulo interno, ex: "comercial-filial-01")
  - phone_e164 (número vinculado quando conectado)
  - evolution_instance (nome da instance na Evolution — único)
  - api_key_hash (nunca guardar a key em claro)
  - api_key_prefix (para UX de suporte, ex: zpg_live_ab12…)
  - status: pending_pair | active | paused | revoked | rebind_required
  - rate_limit_per_minute
  - created_at / updated_at / last_connected_at

5.2 Isolamento garantido
  Rede / processo:
  - Workers NÃO usam uma session global.
  - Cada job carrega sender_id; o worker só usa a instance Evolution daquele sender.
  - Credenciais do Sistema X autenticam 1:1 com o sender (Bearer daquele cadastro).

  Dados:
  - Mensagens sempre com FK sender_id.
  - Row Level guard no service: job.sender_id deve bater com a instance usada.
  - Logs com sender_id, never misturar phones de senders diferentes no mesmo job.

  Fila:
  - Exchange: zap.send
  - Routing key: sender.{sender_id}
  - Queue dedicada: q.sender.{sender_id}  (ou sharding por hash se muitos senders)
  - Prefetch baixo (ex: 1–5) para não monopolizar um número.

5.3 Rebind / substituir o Zap do cadastro
  Caso de uso: troca de chip/aparelho sem mudar o Sistema X.

  Fluxo:
  1) Admin marca sender como rebind_required (pausar envios).
  2) Logout/delete da instance antiga na Evolution (ou rotaciona instance name).
  3) Cria nova instance e gera QR.
  4) Escaneia no novo celular.
  5) Atualiza phone_e164 + status=active.
  6) Retoma consumindo a fila do MESMO sender_id.

  Contrato do Sistema X permanece:
    POST /v1/messages  + Bearer <mesma api_key do cadastro>
  O "zap da mensagem" passa a ser o novo aparelho vinculado.


6. CONTRATO DA API (Sistema X → Gateway)
--------------------------------------------------------------------------------
Base URL (host): http://localhost:8141

6.1 Autenticação
  Authorization: Bearer <SENDER_API_KEY>
  Alternativa header: X-Sender-Key: <SENDER_API_KEY>

  A key identifica o sender. Não existe "account root" no POST de envio.
  (Admin usa outro token: ADMIN_TOKEN, só no painel / rotas /v1/admin/*)

6.2 Criar mensagem (assíncrono)
  POST /v1/messages
  Content-Type: application/json

  {
    "external_id": "erp-order-998877",          // obrigatório p/ idempotência
    "to": "5534999999999",                     // E.164 sem +
    "type": "text",                            // text | (fase2: image, document)
    "body": "Olá, seu pedido saiu para entrega.",
    "metadata": {                              // livre, auditável
      "order_id": "998877",
      "source": "erp-wms"
    },
    "priority": "normal",                      // normal | high
    "schedule_at": null                        // ISO-8601 opcional (fase 2)
  }

  Respostas:
  202 Accepted
  {
    "id": "msg_01H…",
    "external_id": "erp-order-998877",
    "status": "queued",
    "sender_id": "snd_01H…",
    "created_at": "2026-08-07T16:00:00Z"
  }

  200 OK (replay idempotente — mesma external_id já existia)
  401 Unauthorized (key inválida / sender revoked)
  403 Forbidden (sender paused / rebind_required)
  422 Unprocessable Entity (payload inválido)
  429 Too Many Requests (rate limit do sender)

6.3 Consultar status
  GET /v1/messages/{id}
  GET /v1/messages/by-external/{external_id}

6.4 Health
  GET /health          → liveness
  GET /ready           → readiness (DB + RabbitMQ + Redis)

6.5 Admin (protegido por ADMIN_TOKEN)
  POST   /v1/admin/senders                 criar sender + gera api_key (mostra 1x)
  GET    /v1/admin/senders
  GET    /v1/admin/senders/{id}
  POST   /v1/admin/senders/{id}/pair       inicia pairing / retorna QR
  POST   /v1/admin/senders/{id}/rebind     inicia troca de aparelho
  POST   /v1/admin/senders/{id}/pause
  POST   /v1/admin/senders/{id}/resume
  POST   /v1/admin/senders/{id}/rotate-key
  GET    /v1/admin/queue/stats
  GET    /v1/admin/messages?status=failed


7. DADOS (modelo mínimo)
--------------------------------------------------------------------------------
senders
  id, name, phone_e164, evolution_instance, api_key_hash, api_key_prefix,
  status, rate_limit_per_minute, created_at, updated_at, last_connected_at

messages (outbox + auditoria)
  id, sender_id, external_id, to_phone, type, body, metadata_json,
  status, attempts, last_error, evolution_message_id,
  queued_at, processing_at, sent_at, failed_at, dead_at,
  UNIQUE(sender_id, external_id)

delivery_events (append-only)
  id, message_id, event, detail_json, created_at

Regras de dados:
- Nunca deletar mensagens enviadas (retenção configurável, ex: 90 dias).
- Soft-pause de sender não apaga fila; só deixa de consumir / rejeita novos POSTs.
- PII (telefone/corpo): logs com masking parcial (5534****9999).


8. FILA E PROCESSAMENTO (melhor caminho)
--------------------------------------------------------------------------------
Broker: RabbitMQ 3.13 (melhor DX + DLQ + management UI) em vez de só Redis list.
Redis continua útil para: rate limit, locks curtos, cache de estado de connection.

Por que RabbitMQ aqui (e não só Redis):
- Ack / nack / requeue nativos
- DLQ madura
- Routing por sender
- Visibilidade operacional (management UI)

Política de retry:
- max_attempts = 5
- backoff: 15s, 45s, 2m, 5m, 15m
- erros permanentes (número inválido, sender revoked) → dead imediato
- erros transitórios (Evolution down, WhatsApp delay) → retry

Worker:
- consome 1 routing key / queue do sender
- abre "claim" no DB (status=processing, attempts++)
- verifica sender.active e instance connected
- aplica rate limit por sender (Redis token bucket)
- chama Evolution: POST /message/sendText/{instance}
- marca sent + grava evolution_message_id
- em falha: nack com delay / publica delay queue / ou dead


9. INTEGRAÇÃO EVOLUTION (alinhada ao #25, isolada)
--------------------------------------------------------------------------------
Imagem: evoapicloud/evolution-api:v2.3.7 (mesma linha estável do #25)

Por sender:
  instanceName = sender.evolution_instance  (ex: snd_01HABC)
  integration  = WHATSAPP-BAILEYS
  qrcode       = true

Envio texto (exemplo conceitual):
  POST {EVOLUTION_URL}/message/sendText/{instance}
  Header: apikey: {EVOLUTION_KEY}
  Body: { "number": "5534…", "text": "…" }

Webhook Evolution (opcional neste sistema):
  - CONNECTION_UPDATE → atualizar sender.status / last_connected_at
  - NÃO processar conversas inbound com IA (fora de escopo)

Segurança Evolution:
- EVOLUTION_KEY forte, só rede interna Docker.
- Host publica só porta 8142 para QR/admin local.
- Em produção, colocar Traefik/Caddy + auth na frente.

11. DOCKER — ARQUITETURA DE COMPOSE (melhor forma)
--------------------------------------------------------------------------------
Serviços:

  api          → FastAPI (ingress POST + status + admin API)
  worker       → consumidor da fila (escalável: deploy.replicas)
  postgres     → estado + outbox + auditoria
  redis        → rate limit / locks
  rabbitmq     → fila + DLQ
  evolution    → ponta WhatsApp
  admin-ui     → UI estática opcional (profile: ui)
  pgadmin      → profile: tools

Boas práticas aplicadas:
- Networks bridge própria: zap-gateway-net
- Healthchecks em todos os serviços críticos
- depends_on com condition: service_healthy
- Volumes nomeados (não bind de data dir em produção)
- .env + .env.example (segredos nunca commitados)
- API/worker mesma imagem, comando diferente (CMD override)
- Restart: unless-stopped
- Resource limits sugeridos (memória worker/evolution)
- Usuário non-root na imagem da API
- Multi-stage Dockerfile (builder + runtime slim)

14. UX OPERACIONAL (admin humano)
--------------------------------------------------------------------------------
Jornada feliz (primeiro sender):
  1) docker compose up -d --build
  2) abrir http://localhost:8141/docs
  3) criar sender (admin) → recebe api_key UMA vez → guardar no cofre/Sistema X
  4) POST pair → abrir QR (UI ou base64)
  5) celular: WhatsApp → Aparelhos conectados → escanear
  6) status sender=active
  7) Sistema X faz POST /v1/messages com a api_key
  8) acompanhar RabbitMQ http://localhost:15641 (user/pass do .env)
  9) consultar GET /v1/messages/{id}

Princípios UX:
- Feedback imediato no POST (202), nunca fazer integrador esperar o WhatsApp.
- Erros acionáveis (sender_paused, invalid_phone, not_paired).
- QR com TTL e botão "gerar novo".
- Rebind guiado em 3 passos (pausar → novo QR → retomar).

20. DECISÕES DE ARQUITETURA (ADRs curtos)
--------------------------------------------------------------------------------
ADR-001: Outbox no Postgres + RabbitMQ
  Motivo: não perder mensagem se o broker oscilar; fonte de verdade no DB.

ADR-002: Auth do POST = api_key do sender (não tenant genérico)
  Motivo: POST conversa direto com o cadastro do zap; isolamento forçado.

ADR-003: Evolution por instanceName == sender
  Motivo: segregação de sessão WhatsApp; rebind troca a session, mantém sender_id.

ADR-004: Portas 8141+ / 5437 / 6381 / 5671 / 15641 / 5051
  Motivo: convivência com #25 (8000/8085/5432/6379/5050) e demais triggers.

ADR-005: Sem IA neste sistema
  Motivo: responsabilidade única — transporte confiável de mensagens outbound.


21. RESUMO EM UMA FRASE
--------------------------------------------------------------------------------
Sistema X autentica contra um Sender cadastrado, posta a mensagem, o gateway
enfileira com isolamento total, o worker envia pelo WhatsApp vinculado àquele
