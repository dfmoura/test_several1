DECISÃO DE ARQUITETURA:

  O ERP NÃO se casa com um banco só.
  Existe uma CAMADA DE ADAPTER (“BankProvider”) com o mesmo contrato
  interno; cada banco implementa o adapter.

  Produção alvo ........ Sicoob (quando credenciais/convênio existirem)
  Homologação/exemplo ... Inter (documentação rica e onboarding digital)
  Futuro ................ BB, Itaú, Bradesco, Stone, etc. — mesmo contrato

CNAB clássico continua como FALLBACK (retorno de boleto) quando a API
do banco ainda não estiver habilitada.

----------------------------------------------------------------------------------------------------
1. PRINCÍPIOS
----------------------------------------------------------------------------------------------------

 1. TIT- é a verdade financeira no ERP; cobrança bancária é EMISSÃO
    vinculada (cobranca_bancaria_id / nosso número / txid PIX).
 2. Baixa automática só via webhook/retorno CONFIÁVEL + conciliação;
    ambiguidade → fila humana (RECEBIMENTO_BAIXA_COBRANCA).
 3. Cada EMPRESA/CNPJ (filial) tem suas próprias credenciais e contas.
 4. Adapter único: trocar Sicoob↔Inter não reescreve faturamento.
 5. Tarifas bancárias → natureza 3.02.04 (ou subconta acordada).

----------------------------------------------------------------------------------------------------
2. CONTRATO INTERNO DO ADAPTER (BankProvider)
----------------------------------------------------------------------------------------------------

Operações mínimas (todas assíncronas com id de correlação):

  emitir_cobranca(tit_id) → { provider_ref, linha_digitavel, pix_qr,
                               pdf_url, vencimento, status }
  consultar_cobranca(provider_ref) → status
  cancelar_cobranca(provider_ref) → status
  obter_pdf(provider_ref) → bytes/url
  listar_extrato(conta_id, de, ate) → lançamentos[]
  consultar_saldo(conta_id) → saldo
  registrar_webhook(url, eventos) / processar_webhook(payload)

Status canônicos ERP (independentemente do banco):
  EMITIDA | REGISTRADA | PAGA | CANCELADA | VENCIDA | FALHA | ESTORNADA

Mapeamento provider → canônico fica DENTRO do adapter.

----------------------------------------------------------------------------------------------------
3. OBJETOS NO ERP
----------------------------------------------------------------------------------------------------

  Conta financeira .... banco, agência, conta, pix_chave, empresa_id
  Credencial provider . client_id, escopos, cert_ref, ambiente
                        (SANDBOX|PROD), empresa_id
  COB-AAAA-NNNNN ...... cobrança emitida (liga TIT- ↔ provider_ref)
  Webhook log ......... payload resumido + resultado processamento

Prefixo COB- no catálogo de exibição.

----------------------------------------------------------------------------------------------------
4. FLUXO COM TIT-
----------------------------------------------------------------------------------------------------

  1) Faturamento gera TIT- (condição de pagamento)
  2) Financeiro (ou automático) chama emitir_cobranca
  3) Grava COB- + nosso número / txid / QR / PDF
  4) Envia ao cliente (e-mail + WhatsApp Business API — template)
  5) Pagamento: webhook ou retorno CNAB ou conciliação de extrato
  6) Cria BX- + baixa TIT- (parcial/total)
  7) Atualiza limite de crédito

Cancelamento de NF / DEV → cancela cobrança aberta no provider.
