0.2. Estrutura padrão de cada caso de uso (em cada TXT de módulo)
----------------------------------------------------------------------------------------------------

  Cada UC contém:
    • Identificação / nome / prioridade / fase sugerida
    • Atores (primário e secundários / sistemas externos)
    • Pré-condições / pós-condições / garantia (o que NÃO pode acontecer)

    • Fluxos alternativos (ALx)
    • Fluxos de exceção (EXx)
    • Regras de negócio aplicáveis (RN- / D0.x / RF-*)
    • Dados / entidades tocadas
    • Rastreabilidade (Trace → TXT-fonte + RF do SRS)
    • Critérios de aceite testáveis

6. REGRAS DE OURO QUE TODO UC DEVE RESPEITAR
====================================================================================================

  G1  PED é o documento-mestre operacional; nenhum UC inventa “pedido paralelo”.
  G2  Aceite informal (WhatsApp pessoal) NÃO gera PED — só link formal.
  G3  Snapshot do ORC aprovado trava preço/spec/qtde/prazo/condição no PED.
  G4  Produção só libera com crédito OK ou adiantamento com BX.
  G5  Documento fiscal ≠ título financeiro (nascem juntos, conceitos distintos).
  G6  Documento não se apaga — estorna/compensa com trilha.
  G7  Dinheiro e NF são idempotentes (retry/webhook não duplica).
  G8  Naturezas só grupos 1–5; LAI / “caixa 2” inexistente.
  G9  Proibido float binário em dinheiro/qtde/alíquota/custo.
  G10 Multi-empresa: tudo carrega empresa_id; EMP-00002 sem venda até decisão.
  G11 WhatsApp oficial somente via API Meta.
  G12 Contábil/fiscal/folha OFICIAIS ficam com o CONTADOR; ERP alimenta.
