0. REGRAS DE OURO (NÃO NEGOCIÁVEIS)
====================================================================================================

  R0.1  Um único ERP. Pedido (PED) é o documento-mestre operacional.
  R0.2  Produção, estoque, NF, título, cobrança, entrega e baixa vivem no
        mesmo sistema — não viram satélites desconectados nem planilha.
  R0.3  Contábil, fiscal e folha OFICIAIS ficam com o CONTADOR.
        O ERP alimenta com disciplina operacional; NÃO fecha apuração fiscal.
  R0.4  Documento não se apaga — se estorna/compensa com trilha auditável.
  R0.5  Duas camadas de identidade: id BIGINT (motor) + código legível (negócio).
  R0.6  Integrações por adapter (Focus NFe, BankProvider, WhatsApp Meta Cloud API).
  R0.7  Multi-empresa por empresa_id (default EMP-00001). Credenciais isoladas.
  R0.8  LAI / livro paralelo / “caixa 2” NÃO entra no ERP
        (DECISAO_NAO_IMPLEMENTAR_LAI_NO_ERP.txt).
  R0.9  WhatsApp oficial somente via API Meta (nunca conta pessoal / Baileys).
  R0.10 Tudo que mexe em dinheiro ou NF é IDEMPOTENTE (webhook, job, retry).
  R0.11 Proibido ponto flutuante binário para dinheiro, qtde, alíquota e custo.
  R0.12 Exceção (RMA/DEV) não apaga o fluxo feliz — complementa com estorno.

1. VISÃO DO PRODUTO
====================================================================================================

----------------------------------------------------------------------------------------------------
1.1. PROBLEMA
----------------------------------------------------------------------------------------------------

  A RLP opera indústria de etiquetas autoadesivas com fluxo comercial longo
  (orçamento → produção → NF → cobrança → entrega → baixa), regras fiscais de MG,
  estoque de bobinas/materiais com sobra/retalho, e equipe enxuta. Operar isso em
  planilha + WhatsApp pessoal + emissor fiscal isolado gera:
    • perda de trilha (quem aprovou, o que foi produzido, o que foi cobrado);
    • risco de crédito e cobrança duplicada;
    • dificuldade de migrar Simples → Lucro Real com dados coerentes;
    • custo operacional alto e dependência de conhecimento tácito.

----------------------------------------------------------------------------------------------------
1.2. SOLUÇÃO
----------------------------------------------------------------------------------------------------

  ERP monólito modular, web, multi-empresa controlada, cobrindo a cadeia
  operacional completa ORC→caixa + exceções (RMA/DEV/compras/remessa) +
  visão gerencial interna + export disciplinado ao contador.

----------------------------------------------------------------------------------------------------
1.3. ATORES
----------------------------------------------------------------------------------------------------

  Internos: ADMIN, FISCAL, FINANCEIRO, COMERCIAL, PRODUCAO, COMPRAS,
            EXPEDICAO (opcional), CONSULTA.
  Externos: Cliente (link de aprovação de orçamento), Contador (export/consulta),
            Focus NFe, Banco (Inter sandbox / Sicoob prod), Meta WhatsApp,
            Transportadora (fase 2).

----------------------------------------------------------------------------------------------------
1.4. FORA DE ESCOPO (EXPLÍCITO)
----------------------------------------------------------------------------------------------------

  • Apuração/fechamento fiscal oficial (SPED/obrigação principal).
  • Folha oficial completa (só pagamento gerencial + import/export).
  • LAI / livro auxiliar / caixa 2 dentro do ERP.
  • Ativação de venda em EMP-00002 sem parecer Contador + Direção.
  • Microsserviços enterprise / EKS / NAT+ALB+Fargate como padrão dia-1.
  • CT-e / API transportadora (FRETE Fase 2 — backlog).
  • Assinatura eletrônica de canhoto (opcional pós go-live).

2. CONTEXTO E DIAGRAMA LÓGICO
====================================================================================================

  Fluxo feliz:

    ORC → (link) aceite → PED
             │
             ├─ crédito/sinal ok → LIBERADO
             │
             ├─ item PRODUCAO → OP → estoque MP→sobra→PA → conclusão
             ├─ item SERVICO  → OS → conclusão
             └─ item REVENDA  → separação
                      │
                      ▼
                NF (Focus) + TIT → COB (banco) → ENT → confirmação
                      │                              │
                      ▼                              ▼
                     BX ← webhook/extrato/CNAB     (MSG WhatsApp status)

    Exceção: RMA → CQ → DEV / reposição / crédito
    Paralelo: COT/OC; REM; COM; BEM preventivo; inventário

  Arquitetura lógica:

                    Clientes (HTTPS) — Web + mobile leve
                           │
                    API ERP (auth, RBAC, empresa_id)
                           │
           ┌───────────────┼───────────────┐
           │               │               │
        Workers         PostgreSQL      Object Storage
        (filas+DLQ)     (+ locks)       (XML/PDF/anexos)
           │
     Focus │ BankProvider │ Meta WhatsApp │ e-mail (SES)

3. MÓDULOS DO SISTEMA (BOUNDED CONTEXTS)
====================================================================================================

  M01 Cadastros .......... PAR, produtos MP/EMB/REV/PA/SVC, usuários, perfis, parâmetros
  M02 Comercial .......... ORC (versão, cenário, gordura, crédito, aceite) → PED
  M03 Produção / PCP ..... OP, OS, apontamento, conclusão, manutenção BEM-
  M04 Estoque ............ MOV, inventário, sobra/retalho, industrialização REM-
  M05 Fiscal ............. NF-e/NFS-e via Focus; metadados; sem fechamento oficial
  M06 Financeiro ......... TIT, COB, BX, aging, crédito, naturezas 1–5, contas
  M07 Compras ............ COT, OC, urgência, entrada XML
  M08 Pós-venda .......... RMA, DEV, garantia, amostra/protótipo
  M09 Integrações ........ BankProvider, WhatsApp MSG-, Focus, jobs de cadência API
  M10 Gerencial .......... DRE interno, patrimônio, RH pagamento, export contador
  M11 Plataforma ......... auth, auditoria, filas, arquivos, multi-empresa, observabilidade

  Regra de dependência: módulos apontam para o PED (mestre), não inventam
  pedido paralelo. Produção consulta PED; não cria “sistema de produção”.

15. IMPLANTAÇÃO E CRITÉRIOS DE ACEITE
====================================================================================================

----------------------------------------------------------------------------------------------------
15.1. FASES (estratégia_implantacao_ja)
----------------------------------------------------------------------------------------------------

  FASE 1 — Entrada em produção (virada):
    • Cadastros clientes/produtos necessários
    • Estoque na data da virada
    • Operação do dia: ORC→PED→OP/OS→NF→TIT→COB→ENT→BX
    • Focus homologado; BankProvider sandbox Inter
    • Sem depender de histórico milenar importado

  FASE 2 — Endurecimento:
    • Histórico seletivo (XML saída legado se necessário)
    • WhatsApp templates oficiais em produção
    • Sicoob prod (credenciais)
    • RMA/DEV homologados com 1 caso real controlado
    • Export contador/folha homologado

  FASE 3 — Expansão controlada:
    • Discussão EMP-00002 (só com parecer)
    • Frete/CT-e fase 2
    • Automações avançadas (régua, recorrência fina)

----------------------------------------------------------------------------------------------------
15.2. CRITÉRIOS DE ACEITE GO-LIVE (mínimos)
----------------------------------------------------------------------------------------------------

  CA-01  Criar ORC → enviar link → aceite cliente → nascer PED com snapshot correto.
  CA-02  Crédito bloqueia/libera produção conforme regra; adiantamento só libera após BX.
  CA-03  OP consome MP, registra sobra e gera PA; inventário concilia.
  CA-04  Emitir NF Focus sem duplicar (retry idempotente); TIT e COB gerados.
  CA-05  Webhook/baixa NÃO gera BX duplicada; ambíguo cai em fila humana.
  CA-06  ENT gera status e MSG WhatsApp (quando integração ligada).
  CA-07  DEV estorna fiscal+estoque+financeiro sem apagar origem.
  CA-08  Multi-empresa: documento EMP-00001 não “pula” para EMP-00002.
  CA-09  Tentativa de criar LAI/natureza 9.xx rejeitada / inexistente no produto.
  CA-10  Backup restaurado com sucesso em exercício documentado.
  CA-11  Decimal: casos de regressão de arredondamento / custo médio passam.
  CA-12  Perfis SoD impedem pares incompatíveis (ou exige controle compensatório
         explicitamente configurado e auditado).
