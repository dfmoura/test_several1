SUMÁRIO EXECUTIVO
================================================================================

Este estudo trata **somente** do domínio Compras.gov / PNCP. Trata-se de um
**sistema novo**, construído do zero: banco vazio, tabelas acessórias novas,
usuários criados no bootstrap e coleta iniciando pela API oficial sem importar
dados de instalações anteriores.

O projeto em trigger/23 serve apenas como **referência de padrões** (coleta PNCP,
normalizers, auth, Docker) — não há migração, compatibilidade retroativa nem
reaproveitamento de SQLite/CSV existentes.

O protótipo de referência era municipal (OSB Uberlândia, singleton, 4 usuários).
O novo sistema nasce já multi-filial:

A construção exige:

  1. Hierarquia Matriz → Filiais (cidades) → UASGs
  2. Matriz OSB Nacional: CNPJ 10.498.528/0001-96 (sede)
  3. Filiais por cidade, ex.: OSB Uberlândia 23.497.346/0001-42
  4. Sede: 1 admin + 3 consulta (administração centralizada de todas filiais)
  5. Cada filial: 4 usuários de consulta (somente leitura da própria unidade)
  6. Sede com visão consolidada/analítica; filiais isoladas por escopo
  7. Coleta Compras.gov inalterada na origem (mesma API), 1×/dia de madrugada
  8. Escala proporcional: cada nova cidade aumenta volume de coleta
  9. Docker, cloud-agnostic, poliglota-ready
 10. Enriquecimento CNPJ via APIs públicas gratuitas (Brasil API + Receita WS)
 11. Resolução de endereço/CEP via APIs CEP gratuitas + lat/lng via OpenStreetMap
 12. **Janela greenfield**: acertar banco, schema, migrations e pacotes **agora**
     — sem dívida técnica herdada do protótipo municipal

**Decisão recomendada (melhor caminho):**

  Novo monólito FastAPI com separação lógica front/back, modelo multi-filial
  desde o dia 1, **PostgreSQL + Alembic** desde a Fase 0 (SQLite só em testes
  unitários), pacotes `models/` por domínio, escopo centralizado em `escopo.py`,
  cache unificado de APIs externas. Coleta por filial com fila sequencial —
  sem microserviços na v1.

2.2 Princípios de ramificação (decisões)
----------------------------------------

  A) Matriz ≠ município monitorado
     O CNPJ 10.498.528/0001-96 ancora a organização OSB nacional (sede).
     Cada filial tem CNPJ próprio da entidade OSB local e IBGE do município
     onde atua — não confundir CNPJ da OSC com CNPJ dos órgãos públicos
     monitorados (prefeitura, autarquias etc.).

  B) UASGs pertencem à filial, não à matriz
     A sede enxerga todas; a filial enxerga só as UASGs que aderiu no Setup.

  C) Administração só na sede
     Filiais não têm admin local — reduz superfície de ataque, garante
     política uniforme de coleta, tokens IA, agendamento e cadastro.

  D) Dados transacionais particionados por filial
     Contratações/itens/contratos filtrados via UASG → observatorio_id.
     Dimensões globais (fornecedor, catálogo) compartilhadas com deduplicação.

  E) Compras.gov é a **única** fonte de dados
     Todo observatório (sede e filiais) opera exclusivamente sobre a API
     Dados Abertos Compras.gov / PNCP. Sem CSV municipal, sem painéis
     externos, sem segunda base paralela.

3.3 Particionamento dos dados Compras.gov
-----------------------------------------

  Opção recomendada: **filtro por UASG → observatório** (sem duplicar fatos)

    - compras_uasgs permanece dimensão global (codigo_uasg UNIQUE nacional)
    - Nova tabela ponte: observatorio_uasg (unidade_observatorio_id, codigo_uasg)
    - Queries de filial: JOIN contratação → uasg → observatorio_uasg
                         WHERE unidade_observatorio_id = :ctx
    - Queries sede consolidada: sem filtro OU filtro opcional por filial

  Alternativa (descartada para v1): observatorio_id em cada linha fato
    — mais simples de filtrar, porém redundante e arriscado na coleta
    (UASG já é chave natural de escopo municipal).

  Campos internos OSB (observador_id etc.): permanecem; escopo validado
  na API ao vincular observador à filial do usuário.

-------------------------------------

  ┌──────────────────────────────────────────────────────────────────────────┐
  │ coleta_fila_execucao                                                     │
  ├──────────────────────────────────────────────────────────────────────────┤
  │ PK id                                                                    │
  │ FK unidade_observatorio_id                                               │

  │ iniciado_em, finalizado_em, resumo_json, log_truncado                    │
  │ UNIQUE parcial: 1 executando por filial; lock global opcional            │
  └──────────────────────────────────────────────────────────────────────────┘

  Agendamento sede (02:00 America/Sao_Paulo):
    1. Admin configura janela e ordem das filiais ativas
    2. Scheduler monta fila coleta_fila_execucao para cada filial
    3. Worker processa SEQUENCIALMENTE (respeita rate limit API Compras.gov)
    4. Por filial: executar pipeline Compras.gov com UASGs da filial
    5. Ao fim de cada filial OK → job CNPJs pendentes **da filial**
    6. Registra execucao agregada + detalhe por filial no Setup sede

3.5 Bootstrap inicial (primeira instalação — sem migração)
----------------------------------------------------------

  Sequência na subida do container / primeiro acesso:

    1. `alembic upgrade head` cria **todas** as tabelas vazias (camadas A–E,
       seção 4.4) — não usar create_all em produção
    2. Seed mínimo: `organizacao` matriz OSB (CNPJ 10.498.528/0001-96)
    3. Bootstrap auth: primeiro usuário vira `sede.admin` (tela ou env)
    4. Admin sede cadastra filiais (ex.: Uberlândia 23.497.346/0001-42 + IBGE)
    5. Sync UASGs por filial → aderir unidades no Setup
    6. Primeira coleta manual ou agendada popula dados **somente via API**

  Não importar:
    - licitacoes.db / CSVs / backups do trigger/23
    - usuários, sessões ou configs de instalação anterior
    - rotinas de compat (`obter_raiz`, singleton id=1, etc.)

  Coexistência: trigger/23 e o novo sistema podem rodar em paralelo (portas
  diferentes) até o corte operacional — sem sync entre bases.


================================================================================
4. MELHORIAS ESTRUTURAIS E BANCO — MOMENTO DE ACERTAR TUDO (GREENFIELD)
================================================================================

Com a visão consolidada (matriz → filiais → UASGs → coleta → CNPJ/CEP/OSM),
**este é o único momento** em que mudar estrutura tem custo baixo. Depois que
filiais entrarem em produção, refactor de schema dói. Decisão: **não replicar**
limitações do trigger/23; implementar o desenho certo desde a Fase 0.

4.1 Princípio orientador
------------------------

  Referência trigger/23 = prova de conceito municipal (SQLite monolítico,
  database.py único ~1400 linhas, `_migrate_*` ad hoc, singleton, sem tenant).

  Novo sistema = produto nacional multi-filial. Copiar **lógica de integração
  PNCP**; **não** copiar forma de persistência nem organização de código.

4.2 Banco de dados — PostgreSQL desde o dia 1 (decisão)
-------------------------------------------------------

  ┌────────────────────┬─────────────────────┬──────────────────────────────┐
  │ Aspecto            │ Referência (evitar) │ Greenfield (adotar)          │
  ├────────────────────┼─────────────────────┼──────────────────────────────┤
  │ SGBD produção      │ SQLite arquivo      │ PostgreSQL 16+ (container)   │
  │ SQLite             │ produção            │ só pytest / dev offline      │
  │ Migrations         │ create_all + patches│ Alembic versionado           │
  │ Tipos JSON         │ TEXT + json.dumps   │ JSONB (Postgres)             │
  │ Datas              │ DATETIME naive      │ TIMESTAMPTZ (UTC)            │
  │ Valores monetários │ float / string      │ NUMERIC(18,4)                │
  │ Concorrência coleta│ lock em memória     │ advisory lock / fila DB      │
  │ Backup             │ copiar arquivo .db  │ pg_dump / volume + retenção  │
  └────────────────────┴─────────────────────┴──────────────────────────────┘

  Docker Compose (produção):
    services: app + postgres (+ caddy profile https)
    DATABASE_URL=postgresql+psycopg://osb:***@postgres:5432/osb_licitacoes

  Motivos para Postgres **agora** (não “depois de 10 filiais”):
    - Multi-filial + coleta noturna + fila + geocode = escritas concorrentes
    - JSONB para config filial, resumo coleta, payload cache
    - Índices parciais (ex.: sessões ativas, fila pendente)
    - Escalar cloud sem trocar SGBD no meio do caminho

4.3 Migrations — Alembic (obrigatório)
--------------------------------------

  Nunca depender de `Base.metadata.create_all()` em produção.

  Estrutura:
    alembic/
      versions/
        001_organizacao_auth.py
        002_compras_core.py
        003_geo_cache.py
        004_coleta_fila.py
        ...

  Bootstrap pós-migrate:
    - seed `organizacao` matriz (SQL ou script idempotente `scripts/seed.py`)
    - bootstrap admin via API ou env

  Testes: SQLite in-memory ou Postgres efêmero (testcontainers opcional).

4.4 Organização do schema — camadas lógicas
-------------------------------------------

  Prefixos / schemas Postgres (ou prefixo tabela) para clareza:

  CAMADA A — TENANT OSB (multi-filial)
    organizacao
    unidade_observatorio
    unidade_compradora
    uasg_catalogo_municipio
    observatorio_uasg          ← ponte escopo (substitui “filtro implícito”)

  CAMADA B — COMPRAS.GOV / PNCP (fatos e dimensões oficiais)
    orgao, uasg, fornecedor, modalidade, catalogo_item
    contratacao, contratacao_item, contratacao_resultado, contrato
    (+ staging opcional: coleta_staging_json — ver 4.5)

  CAMADA C — OSB INTERNO (marcações do observatório)
    observador                 ← FK unidade_observatorio_id (não global solto)
    contratacao_anotacao       ← observador, tags, notas (separar de payload PNCP)
    auditoria_evento           ← sede admin: quem fez o quê (v1, não “fase 2”)

  CAMADA D — OPERAÇÃO
    usuario, sessao
    coleta_agendamento_config
    coleta_fila_execucao
    coleta_execucao_log        ← log truncado por filial/run

  CAMADA E — ENRIQUECIMENTO EXTERNO (cache unificado)
    api_cache                  ← CNPJ, CEP, geocode (tipo + chave + JSONB + TTL)
    endereco_geocode           ← ou subtipo em api_cache + tabela normalizada

  Regra: fatos PNCP **nunca** misturam colunas OSB no mesmo UPDATE da coleta.
  Campos internos em tabelas C ou JSONB sidecar com FK explícita.

4.5 Melhorias no modelo Compras.gov (vs referência)
---------------------------------------------------

  a) Nomenclatura limpa (sem prefixo `compras_` redundante se schema `pncp`):
       pncp.contratacao em vez de compras_contratacoes — opcional, mas legível.

  b) Chaves naturais indexadas desde o início:
       UNIQUE numero_controle_pncp
       UNIQUE (codigo_uasg) em uasg
       UNIQUE ni_fornecedor em fornecedor
       INDEX (codigo_uasg, ano_compra) em contratacao
       INDEX (unidade_observatorio_id) via join uasg — ver ponte

  c) Resultados homologados (07.3) como entidade explícita — já na referência;
     garantir FK fornecedor + item + contratacao sem ambiguidade.

  d) Staging opcional (recomendado para robustez de coleta):
       coleta_staging (id, fonte, endpoint, chave, payload_jsonb, coletado_em)
     Pipeline: API → staging → upsert normalizado (permite replay/debug).

  e) Preservação na sync (padrão já validado):
       CAMPOS_PRESERVADOS = observador_id, anotacoes internas
     Coleta oficial não apaga marcações OSB.

  f) Eliminar do greenfield:
       - tabelas weblicitacoes / licitacoes portal prefeitura (fora escopo)
       - qualquer resquício Power BI
       - sistema_raiz, SistemaConfig monolítico

4.6 Multi-tenant — escopo na arquitetura, não só na query
---------------------------------------------------------

  Decisão revisada (melhor que só JOIN UASG):

    unidade_compradora liga filial ↔ codigo_uasg (adesão Setup)
    contratacao.codigo_uasg → join unidade_compradora → filial

  Opcional performance (recomendado se >20 filiais):
    contratacao.unidade_observatorio_id denormalizado na coleta
    (preenchido no upsert a partir da UASG — acelera dashboard sede)

  observador.unidade_observatorio_id NOT NULL — observador é da filial
  usuario: CHECK (escopo=sede → filial_id IS NULL; escopo=filial → NOT NULL)

  escopo.py (único ponto):
    resolve_ctx(request) → uasgs_permitidas | filial_id | consolidado
    apply_escopo(stmt, ctx) → modifica SQLAlchemy select

  ├──────────────────────────────────────────────────────────────────────────┤
  │ PK id                                                                    │
  │ tipo              cnpj | cep | geocode                                   │
  │ chave             CNPJ 14 díg / CEP 8 díg / hash endereço                  │
  │ payload_jsonb     resposta normalizada + raw opcional                      │
  │ fonte             brasilapi | receita_ws | viacep | nominatim              │

  │ criado_em / atualizado_em                                                │
  │ UNIQUE (tipo, chave)                                                     │

  fornecedor.api_cache_id FK opcional; geocode reutilizável entre fornecedores.

6. COLETA COMPRAS.GOV EM ESCALA
================================================================================

6.1 Impacto do crescimento
--------------------------

  Cada nova filial adiciona:
    - N uasgs × M anos × modalidades × fases (07, 07-resultados, 05)
    - Enriquecimento CNPJ vencedores (job pendentes) proporcional ao volume
    - Tempo de janela noturna cresce linearmente (~ linear com UASGs)

  Estimativa operacional (ordem de grandeza):
    - 1 filial (8 UASGs, 2 anos): ~15–45 min (experiência Uberlândia)
    - 10 filiais: ~2,5–7,5 h se sequencial na mesma janela
    - 30 filiais: exige janela estendida ou paralelismo controlado

6.2 Estratégia de orquestração (recomendada v1 → v2)
----------------------------------------------------

  V1 (implementar primeiro — alinhada ao código atual):
    - Fila sequencial por filial dentro do scheduler existente
    - Rate limit global: COMPRAS_PNCP_REQUEST_DELAY_SEC (já existe)
    - Lock: 1 job coleta global OR 1 job por filial (escolher 1 global v1)
    - Horário configurável sede; filiais não disparam coleta manual

  V2 (quando > ~15 filiais ou janela > 4h):
    - Worker coleta em container separado (mesma imagem, CMD diferente)
    - Fila persistida + semáforo HTTP (Redis opcional)
    - Postgres advisory locks para jobs

  NÃO recomendado agora:
    - Celery/RabbitMQ/Kafka para 3–10 filiais (overengineering vs detalhes/00)
    - Coleta paralela irrestrita (risco 429/throttle Compras.gov)

6.3 API Compras.gov — inalterada na origem
------------------------------------------

  Base: https://dadosabertos.compras.gov.br
  Cliente: ComprasGovClient (httpx, paginação, delay)
  Módulos: 05 UASG, 07 Contratações, 07 Itens/Resultados, 10 Fornecedor, 01/02 Catálogo

  Por filial, parâmetros de coleta:
    - unidadeOrgaoCodigoUnidade = cada UASG ativa da filial
    - codigoMunicipioIbge = IBGE da filial (sync catálogo UASG)
    - Anos: config filial ou global sede (ano_inicial → corrente)

6.4 Sincronização de UASGs por filial
-------------------------------------

  Reutilizar fluxo Setup (sincronizar catálogo município → aderir UASGs):
    - Endpoint sede: POST /api/sistema/filiais/{id}/uasgs/sync
    - Admin sede cadastra filial (CNPJ OSB + IBGE) → sync automático
    - Filial consulta não vê Setup; sede escolhe UASGs monitoradas

7. APIS PÚBLICAS GRATUITAS — CNPJ, CEP E OPENSTREETMAP
================================================================================

Camada complementar ao Compras.gov: enriquece fornecedores vencedores, sedes
de filiais OSB e endereços para plotagem geográfica. Todas gratuitas; exigem
cache agressivo, fallback encadeado e respeito a limites de uso.

7.1 CNPJ — Brasil API + Receita WS (decisão oficial)
----------------------------------------------------

  Objetivo:
    - QSA, CNAEs, porte, natureza jurídica, endereço completo (logradouro, CEP)
    - Cadastro/atualização de unidade_observatorio (CNPJ OSB filial)
    - Job noturno de CNPJs pendentes (vencedores sem enriquecimento)

  Cadeia recomendada (ordem de tentativa):

    1) Brasil API (primária)
       GET https://brasilapi.com.br/api/cnpj/v1/{cnpj}
       - Gratuita, JSON estável, boa cobertura de campos
       - Tratar 404 (CNPJ inexistente) vs 429/5xx (fallback)

    2) Receita WS — Pública CNPJ.ws (secundária)
       GET https://publica.cnpj.ws/cnpj/{cnpj}
       - Fallback quando Brasil API falha ou está indisponível
       - Normalizar payload diferente para o mesmo schema interno

    3) Fallbacks opcionais (já no trigger/23 — manter só se necessário):
       - Minha Receita (https://minhareceita.org/{cnpj})
       - CNPJá Open (https://open.cnpja.com/office/{cnpj})

  Schema interno único (independente da fonte):
    cnpj, razao_social, nome_fantasia, situacao_cadastral, porte, cnae_principal,
    cnaes_secundarios[], logradouro, numero, complemento, bairro, cep, uf,
    codigo_municipio_ibge, municipio, qsa[], fonte_cnpj, cnpj_dados_json,
    enriquecido_em

  Persistência:
    - fornecedor + endereco_geocode / api_cache (tabelas novas)
    - unidade_observatorio (CNPJ filial OSB)
    - TTL via api_cache.valido_ate (CNPJ 30d, CEP 90d…)

  Rate limit / fila multi-filial:
    - Intervalo entre consultas: CNPJ_PUBLICO_LOTE_INTERVALO_SEC (ex.: 3s)
    - Backoff em 429: CNPJ_PUBLICO_LOTE_BACKOFF_SEC (ex.: 30s)
    - Job por filial na cadeia noturna; semáforo global entre filiais

7.2 CEP — APIs públicas gratuitas
---------------------------------

  Objetivo:
    - Completar/normalizar endereço quando Compras.gov ou CNPJ trazem só CEP
    - Obter logradouro, bairro, município, UF, IBGE antes da geocodificação

  Cadeia recomendada:

    1) Brasil API CEP (primária)
       GET https://brasilapi.com.br/api/cep/v2/{cep}
       - Retorna CEP, state, city, neighborhood, street, location (coords IBGE)

    2) ViaCEP (secundária)
       GET https://viacep.com.br/ws/{cep}/json/
       - Amplamente usada; tratar campo "erro": true

    3) OpenCEP (terciária)
       GET https://opencep.com/v1/{cep}
       - Fallback simples, JSON enxuto

  Módulo sugerido: app/endereco/cep_publico.py
    - consultar_cep(cep) → dict normalizado
    - validar CEP (8 dígitos); aceitar com/sem hífen
    - cache em tabela api_cache (tipo=cep) — seção 4.7

  Fluxo:
    endereço incompleto → consulta CEP → merge campos faltantes → geocode OSM

7.3 Geocodificação — OpenStreetMap (Nominatim)
----------------------------------------------

  Objetivo:
    - latitude / longitude para plotar fornecedores, filiais OSB e agregações
    - Mapas sede (Brasil) e filial (regional)

  Serviço: Nominatim (OpenStreetMap Foundation)
    GET https://nominatim.openstreetmap.org/search
      ?q={endereco_completo}&format=json&limit=1&countrycodes=br

  Regras de uso (obrigatórias):
    - User-Agent identificável: OSB-Observatorio/{versao} (+ e-mail contato)
    - Máximo ~1 requisição/segundo (NOMINATIM_MIN_INTERVAL_SEC=1.1)
    - Cache persistente — NUNCA geocodificar o mesmo endereço duas vezes
    - Atribuição OSM visível no mapa: "© OpenStreetMap contributors"

  Alternativa de coordenadas:
    - Brasil API CEP v2 já pode trazer location.coordinates (lat/lng)
    - Preferir CEP v2 quando disponível; Nominatim só se faltar lat/lng

  Persistência sugerida:

  ┌──────────────────────────────────────────────────────────────────────────┐
  │ endereco_geocode                                                         │
  ├──────────────────────────────────────────────────────────────────────────┤
  │ PK id                                                                    │
  │ chave_endereco     VARCHAR(500) UNIQUE  — hash ou string canônica        │
  │ cep, logradouro, numero, bairro, municipio, uf                           │
  │ latitude           DECIMAL(9,6)                                          │
  │ longitude          DECIMAL(9,6)                                          │
  │ fonte              nominatim | brasilapi_cep | manual                    │
  │ precisao           VARCHAR(40)  — rooftop / approximate / centroid       │
  │ geocodificado_em   DATETIME                                              │
  └──────────────────────────────────────────────────────────────────────────┘

  FK opcional: compras_fornecedores.geocode_id, unidade_observatorio.geocode_id

7.4 Visualização — Leaflet + tiles OpenStreetMap
------------------------------------------------

  Biblioteca: Leaflet.js (já usada em localidade.js)

  Tiles (decisão — substituir Carto por OSM):
    https://tile.openstreetmap.org/{z}/{x}/{y}.png
    - attribution: © OpenStreetMap contributors
    - maxZoom conforme política OSM (tipicamente 19)

  Camadas do mapa:

    Sede (consolidado):
      - Marcadores das filiais OSB (lat/lng da sede municipal OSB ou prefeitura-ref)
      - Coroplético Brasil por UF / heatmap municípios (vencedores agregados)
      - Drill-down: clique filial → zoom região

    Filial:
      - Mapa regional (município + entorno)
      - Bolhas/calor: fornecedores vencedores com coords OSM
      - Filtro: valor homologado | quantidade | porte

  Backend:
    - GET /api/geo/distribuicao — estendido com lat/lng quando geocode_id presente
    - GET /api/geo/filiais — pontos das unidades_observatorio para mapa sede
    - Escopo: filial recebe só coords da própria filial + vencedores do escopo

7.5 Orquestração na cadeia noturna
----------------------------------

  Por filial, após coleta Compras.gov OK:

    1. Job CNPJs pendentes → Brasil API → Receita WS (fallback)
    2. Para endereços com CEP sem logradouro → consulta CEP (Brasil API → ViaCEP)
    3. Para registros sem lat/lng → fila geocode Nominatim (1 req/s global)
    4. Atualizar agregações /api/geo/distribuicao

  Prioridade geocode:
    a) Filiais OSB (poucas, uma vez)
    b) Fornecedores vencedores recorrentes (top N por valor)
    c) Demais pendentes (fila background)

7.7 Riscos e boas práticas
--------------------------

  Risco                         Mitigação
  ─────────────────────────────────────────────────────────────────────────
